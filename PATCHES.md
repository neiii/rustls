# FAIM's rustls fork

This is rustls 0.23.46, from the upstream tag `v/0.23.46` (commit `f04804f`), on the `faim` branch of `neiii/rustls`, with the changes below. [FAIM](https://github.com/neiii/faim-http) mirrors the hello each client sends it toward the server (its ADR-0011), and this fork sends that hello. FAIM pins one commit of this branch with `[patch.crates-io]`, never the branch itself.

Every change is listed with its reason, so a rebase onto a later release can redo each one on purpose: start a new branch from the new tag and reapply the commits in `git log v/0.23.46..faim`. Code the fork adds is marked `FAIM:` in a comment, and most of it sits in one new file, `rustls/src/client/hs/template.rs`. The template logic itself (parsing a hello, rendering it, reshaping it for a retry or a PSK, which extensions count as offered) is plain data in faim-http's `crates/faim-template`, which the fork calls and which doesn't know rustls.

`git diff v/0.23.46 faim` shows every change against the release.

## Building and testing

The fork's `rustls` crate depends on `faim-template = "*"`, which crates.io doesn't have. Any version matches, since faim-template takes faim-http's product version, which moves at milestones (faim-http's ADR-0027), and a `[patch.crates-io]` entry only applies when its version meets the requirement. FAIM's own workspace supplies it with `[patch.crates-io]`. Here, this workspace's `[patch.crates-io]` takes it from a faim-http checkout beside this one, at `../faim-http`. faim-template builds on FAIM's nightly toolchain (the `rust` line of faim-http's `mise.toml`), so the fork does too.

- rustls's own tests: `cargo test -p rustls`.
- BoGo: `cd bogo && BOGO_SHIM_PROVIDER=aws-lc-rs ./runme`, with Go installed.

The `faim` workflow (`.github/workflows/faim.yml`) runs both on every push and pull request to this branch, after checking that the `rustls` crate still compiles across upstream's feature builds (no std, either provider). faim-http is private, so the workflow checks it out with the `FAIM_HTTP_TOKEN` secret, a fine-grained token with Contents: read on `neiii/faim-http`. It builds against the faim-http commit named in `FAIM_HTTP_REF`, a one-line file at the root. A commit, not a branch, so a green run says what it was built against. A change here that needs a faim-template change faim-http hasn't merged names the faim-http commit that has it; otherwise the file names a commit on faim-http's `master`. A run started by hand can name another ref with `faim-http-ref`.

A change that touches both repositories merges here first. faim-http then pins the new commit.

## The tree

- **`Cargo.toml`**: `[patch.crates-io]` supplies `faim-template` from `../faim-http` (see above).
- **`Cargo.lock`**: `aws-lc-rs` 1.19.0 and `aws-lc-sys` 0.47.0, the versions FAIM builds with, so the fork's tests run on the crypto FAIM ships, and `faim-template` with its dependencies. A change that bumps `aws-lc-rs` in faim-http's `Cargo.lock` bumps it here too (`cargo update -p aws-lc-rs --precise <version>`).
- **`rustls/Cargo.toml`**: depends on `faim-template = "*"`, so faim-http's version bumps don't break the patch (see above).
- **`FAIM_HTTP_REF`** (new): the faim-http commit the `faim` workflow builds faim-template from (see above).
- **`.github/workflows/`**: upstream's workflows are removed. They build without faim-template, so every one would fail here, and FAIM doesn't need their release or docs jobs. `faim.yml` replaces them, and keeps their feature builds. Their fuzzing and dependency checks aren't replaced here: faim-http's `mise run check` audits the dependency tree it builds this fork into, and fuzzing the template path needs faim-http's corpus.

## The client sends a template's hello

- **`ClientConfig::hello_template`** (`client/client_conn.rs`, default `None` in `client/builder.rs`): the template to send in place of rustls's own hello. `None` leaves the client stock, so FAIM's default upstream leg is unchanged until faim-http#167's switch gate passes.
- **`client/hs/template.rs`** (new): renders the template with fresh values (rustls's random, a session id of the template's length, a fresh key for each key share slot, random bytes for a slot whose group aws-lc-rs can't compute, and GREASE ECH bytes in the client's shape, faim-http#200), and sends it in the record version the template recorded. It reads the hello back with rustls's own decoder to fill `ClientHelloDetails`: the extensions a server may answer (every one the template carries but GREASE and `padding`, so ALPS and certificate compression among them), its cipher suites and its ALPN. It holds the helpers the other patches call.
- **What the server picks is checked against the template's offer, not the config.** Stock rustls offers everything its config has, so it checks a server's pick against the config. A template offers what its client offered, and faim-http's `faim_proxy::template::client_config` enables every group, suite and decompressor aws-lc-rs has, so the fork asks the template (`ClientTemplate::offers_version`, `offers_cipher_suite`, `offers_group`, `offers_signature_scheme`, `offers_certificate_compression`). A pick the template never offered is refused with the error stock rustls gives an unoffered pick. A pick it offered that the fork can't complete is `Error::Shortfall` naming it (faim-http#197 turns that into a passthrough). GREASE values are never offered.
- **`client/hs.rs`**:
  - A connection with a template gets a session id of the template's length (`ClientHelloInput::new`).
  - `start_handshake` hands a template's hello to `template::emit_client_hello`. A config that also asks for real ECH (`EchMode::Enable`) sends real ECH when the template carries an inner hello (see *The client sends a template's real ECH* below), and is refused with `Error::General` otherwise, since the template greases ECH in its client's shape and would silently drop it. A QUIC connection is refused with `Shortfall::Quic`, before any hello goes out: the template carries its client's recorded `quic_transport_parameters`, not the connection's, and FAIM passes QUIC through until it intercepts it (faim-http#167). The SNI goes out without a trailing dot, as stock rustls sends it (RFC 6066).
  - `ExpectServerHello` keeps the template's other key shares (`template_shares`) beside `offered_key_share`, and a TLS 1.3 `ServerHello` takes the share for the group the server picked (`template::choose_key_share`). Stock rustls sends one share and has no use for more. A template's X25519MLKEM768 share doesn't stand in for an X25519 share it didn't send, as stock rustls's hybrid share does for its own.
  - A `HelloRetryRequest` sends the template again reshaped as the client would (`ClientTemplate::retry`), reusing the first hello's keys and ECH bytes, and the random bytes of a slot the fork can't compute when the retry names no group (RFC 8446 §4.1.2). A retry for a group or suite the template didn't offer, or for a group its hello already sent a key share for, is refused. A template's hello may send no key share the fork can complete, so a retry no longer requires one. rustls's own hello always sends one, and where stock rustls would `unwrap` it, the fork fails with `IllegalHelloRetryRequestWithOfferedGroup`.
  - The version and suite checks (`template::check_version`, `template::unknown_cipher_suite`).
  - A template that offered no TLS 1.3 takes a TLS 1.2 `ServerHello` whose random carries the downgrade marker, which every TLS 1.3 server sets when it answers TLS 1.2.
  - A TLS 1.2 server's `record_size_limit` caps what the client sends. A smaller `ClientConfig::max_fragment_size` stays (here and in TLS 1.3).
- **`client/tls13.rs`**:
  - `EncryptedExtensions`: notes ALPS (`application_settings`, 0x4469 or 0x44cd) and applies `record_size_limit`, and keeps what the template offered for the certificate's entries to answer. An answer to any other offered extension rustls doesn't handle is `Shortfall::Extension` (`template::check_unhandled_extensions`), since it can oblige the client to something the fork doesn't do: an acked `max_fragment_length` caps every record. The same goes for a TLS 1.2 `ServerHello`. `trust_anchors` (0xca34, draft-ietf-tls-trust-anchor-ids, which Chrome offers) passes too (faim-http#469): the server's list names the anchors it has paths for, which a client uses only to retry after a certificate error (§5.6), so it obliges the client to nothing in a handshake that succeeds, and the certificate is verified as usual. The draft defines it for TLS 1.3 alone, so a TLS 1.2 `ServerHello` carrying it is still a shortfall.
  - A TLS 1.3 `ServerHello` carrying an extension rustls doesn't parse is refused as `UnexpectedCleartextExtension` (`validate_server_hello`), as stock rustls refuses it as unsolicited. `only_contains` sees only the extensions rustls parses, and a template offers others.
  - `Certificate`: an entry's extension rustls doesn't handle must answer one the template offered, and a delegated credential is a `Shortfall`, since the handshake is then signed with the credential's key.
  - `CompressedCertificate`: the algorithm checked against the template's offer, then against the fork's decompressors.
  - `CertificateVerify`: the scheme checked against the template's `signature_algorithms`, then against what the verifier can check.
  - `Finished`: a server that agreed to ALPS gets the client's `EncryptedExtensions` with its `application_settings` before the client's `Finished`, as Chromium sends it. The settings go out empty until faim-http#198 fills them from the client's HTTP/2 SETTINGS.
- **`client/tls12.rs`**: a `ServerKeyExchange`'s curve and signature scheme checked against the template's offer, then against what aws-lc-rs can compute and verify.
- **`ClientConnectionData`** (`client/client_conn.rs`): `template_alps` and `template_offered`, carried from `EncryptedExtensions` to the states after it.

## The client keeps what the server answered (faim-http#197)

FAIM opens the upstream connection first and answers its client in the shape of what the server sent, so it needs the server's messages, which TLS 1.3 encrypts.

- **`ClientConnection::server_flight`** (`client/client_conn.rs`): the handshake messages the server answered a template's hello with, as `faim_template::ServerFlight` reads them. `None` without a template, so a stock client keeps nothing.
- **`client/hs/template.rs`**: `KeptFlight` holds them. `keep_server_hello` keeps the `ServerHello` as one TLS record in the version it came in.
- **`client/hs.rs`, `client/tls13.rs`, `client/tls12.rs`**: each state that reads one of those messages keeps its bytes as they came. A `CompressedCertificate` is kept as the `Certificate` it decompresses to, with its algorithm, built from the decompressed bytes because encoding the parsed payload again would lose the extensions it doesn't name.

## Resumption (faim-http#199)

FAIM mirrors resumption both ways: it issues its client a ticket for each one the server issues, keeps a store from one to the other, and resumes upstream with the server's ticket when the client resumes with FAIM's.

- **`client/hs.rs`, `client/hs/template.rs`**: a template's hello resumes what `ClientConfig::resumption`'s store hands over, as a stock hello does. `ClientConfig::resumes_session_as_given` skips the store's configuration check, which compares verifiers and client credentials by address: faim-http builds one configuration per connection and files each session under the upstream and certificate check it came from. It is off by default, so a config sharing a store keeps rustls's check. `emit_client_hello` offers the one TLS 1.3 session it holds as a `pre_shared_key` identity through `faim_template::Psk`, and fills its binder in the rendered hello (`tls13::fill_in_template_psk_binder`), since the rendered bytes are what goes in the transcript. `early_data` goes out only when `enable_early_data` is on and the session allows some (`ClientTemplate::without_early_data` otherwise).
- **`KeptFlight::as_flight`**: a resumed handshake has no `Certificate`, so the flight needs only a `ServerHello`.
- **`ClientConfig::hold_early_data`**, **`ClientConnection::early_data_held`** and **`ClientConnection::end_early_data`** (`client/client_conn.rs`, `client/tls13.rs`'s `HoldingEarlyData`, `common_state.rs`): FAIM sends a client's early data on only once that client's handshake with it has completed, which is after the server's `Finished`, so a connection with this set stops there instead of sending `EndOfEarlyData`. `CommonState::early_data_held` says how much early data it may still send: what is written meanwhile goes out as early data, past that, or behind plaintext written before the hold, it waits for the end of the handshake. `is_handshaking` is false while held, so tokio-rustls hands the connection over. While held, the client reads what the server sends behind its `Finished` (faim-http#564): entering the hold moves the decrypter to the server's application traffic secret, derived from the transcript through the server's `Finished` without moving the key schedule on (`KeyScheduleHandshake::set_server_traffic_decrypter`), and `HoldingEarlyData` takes application data as it comes. faim-http's HTTP/2 leg learns the server's `SETTINGS` that way before it sends the client's request as early data. A `NewSessionTicket` sent before the client's `Finished` (BoringSSL sends them when it accepts early data) waits in `HoldingEarlyData`, at most eight of them, since its resumption secret needs that `Finished`, and is handled once the hold ends. `end_early_data` then moves only the encrypter (`KeyScheduleClientBeforeFinished::into_traffic_reading`), so the server's records keep their sequence numbers.
- **`ClientSessionCommon::lifetime_secs`, `ticket` and `server_cert_chain_len`** (`msgs/persist.rs`): what FAIM needs to issue the same ticket hints and count a session against its memory budget.
- **`impl BufRead for ReadEarlyData`** (`server/server_conn.rs`): a server reads a client's early data one record at a time, as `impl BufRead for Reader` reads what follows the handshake. `EarlyDataState::take_received_plaintext` appends one chunk per record, so `fill_buf` returns the rest of the first record and `consume` consumes from it. FAIM copies where a client ended its records toward the server (faim-http#449, faim-http#498), and `Read` alone reads across them.
- **`ServerConnection::issue_tls13_ticket`** (`server/server_conn.rs`, `server/tls13.rs`): issues one ticket after the handshake with a given lifetime hint and early data limit, since a server's tickets arrive at FAIM after FAIM's handshake, and a client's handshake with FAIM may have finished by then. It goes through `ServerConfig::session_storage`, so the ticket is FAIM's to look up.
- **`server/tls13.rs`, `server/template.rs`**: a server template accepts a PSK where the server's answer resumed (`Answer::resumed`), and sends the identity it chose. The early data decision runs after the template's ALPN applies, and only accepts where the server accepted FAIM's (`Answer::early_data`); otherwise the template's `early_data` is left out (`Answer::without_early_data`). A client whose PSK can't be resumed though the server resumed gets a full handshake and a shortfall.

## Messages and errors

- **`Error::Shortfall(faim_template::Shortfall)`** and **`PeerMisbehaved::IllegalRecordSizeLimit`** (`error.rs`).
- **`ExtensionType::RecordSizeLimit`** (`msgs/enums.rs`) and **`ServerExtensions::record_size_limit`** (`msgs/handshake.rs`): read so a template that offered it can honour the server's limit. A stock client never offers it, so a server that sends it is still refused as unsolicited.
- **`CertificateExtensions::unknown_extensions`** (`msgs/handshake.rs`): decoding a certificate entry no longer refuses an extension rustls doesn't handle. It records the type, and the state that reads the certificate decides, since only it knows what its hello offered. `CertificatePayloadTls13::unknown_extensions` lists them. A stock client and the server refuse any, with the alert and error decoding gave before (`DecodeError`, `UnknownCertificateExtension`).
- **`msgs/handshake_test.rs`**: the sample payloads gain the two new fields.

## The server

- **`ServerConfig::ech_retry_configs`** (`server/server_conn.rs`, default `None` in `server/builder.rs`; sent from `server/tls13.rs`): ECH configs to send a client whose outer hello offered ECH that the server didn't accept (RFC 9849 §7.1); an inner hello, whose ECH was accepted, gets none. Configs that don't parse, or parse to an empty list the extension doesn't allow, are left out with a warning rather than failing the handshake after `ServerHello` or sending an invalid extension. FAIM's test harness uses it to show that a greased ECH ignores them (faim-http#200). A server template sends the server's own as part of its `EncryptedExtensions`, in their place.
- **`server/tls13.rs`**: a client certificate entry with an extension rustls doesn't handle is refused here, where decoding used to refuse it (see `CertificateExtensions` above).

## The client sends a template's real ECH (faim-http#601)

FAIM opens a client's real ECH under its own keys (faim-http#600), and sends it on to the server under the provider's own config, from the client's outer and inner hellos, so the server sees the handshake it would see without FAIM. faim-template holds the inner hello as plain data: `ClientTemplate::inner`, read from the `EncodedClientHelloInner` the client sealed (`ClientHello::from_encoded_inner`), rendered padded to the length the client sealed and expanded against the outer hello as a server rebuilds it (`ClientTemplate::render_inner`).

- **`client/hs.rs`**: `start_handshake` makes an `EchState` from `EchMode::Enable` for a template with an inner hello and hands it to `template::emit_client_hello`, and a `HelloRetryRequest` hands it on. A template's outer hello may offer TLS 1.2 beside real ECH, and a config sending real ECH speaks TLS 1.3 alone, so a server that picks TLS 1.2 fails the handshake as stock rustls fails it: that `ServerHello` comes before any certificate, so it can't say the ECH was rejected securely (RFC 9849 §6.1.6), and taking it as a rejection would let an injected one turn the client's ECH off.
- **`client/hs/template.rs`**: `seal_inner` renders the outer hello under the config's id and suite (`ClientTemplate::under_ech_config`) and the public name, the inner hello with the connection's inner random and SNI, and the outer hello's fresh keys group by group: an inner key share for a group the outer hello sends none for is `Shortfall::InnerKeyShare`, so the fork keeps one key exchange per group. A session resumes in the inner hello, its binder over the inner transcript, and the outer hello carries a GREASE PSK of the inner one's shape (§6.1.2); early data derives from the inner transcript and random (§6.1). The payload is sealed with the outer hello's body, its payload zeroed, as AAD (§5.2). A `HelloRetryRequest` that accepted the ECH gets the inner hello sealed again with the same context and no `enc` (§6.1.5); one that rejected it gets the outer hello again with the first hello's ECH bytes, as stock rustls sends them, still naming the public name and with a GREASE PSK in the inner one's shape, so neither the inner host nor the session goes out in the clear.
- **`client/ech.rs`**: `EchState` hands the template what it seals with (`template_config`, `template_enc`, `template_tag_len`, `seal_template_inner`) and takes the inner hello into its transcript (`take_template_inner`). From there the stock path checks the server's acceptance, in the `ServerHello` and a `HelloRetryRequest`, switches to the inner transcript, and on a rejection verifies the certificate for the public name and ends with `ech_required` and the server's retry configs. The server's picks are still checked against the outer template: the inner hello takes the outer's key shares, and the clients FAIM has recorded offer the same in both.
- **`ClientConnection::ech_inner_hello`** (`client/client_conn.rs`): the inner hello a client last sealed into real ECH, as its transcript has it, from rustls's own ECH hello and a template's alike, for faim-http to record on the upstream leg.
- **`Tls13ClientSessionValue` is `Clone`** (`msgs/persist.rs`): faim-http offers a session again on its one retry under a server's retry configs, since the server never saw the first offer, sealed inside the ECH it rejected.
- **`OpenedEch::encoded_inner`** (`server/ech.rs`): the `EncodedClientHelloInner` as it decrypted, which faim-http reads the client's inner hello from, its `ech_outer_extensions` and padding included.
- **`rustls/tests/faim_ech.rs`**, module `template`: a template hello under a config reaches a server holding its key, which accepts the ECH and reads the inner hello's SNI, across a `HelloRetryRequest` too, and resumed inside the inner hello; its inner hello is its client's but for the fresh fields, padded to the client's length; a server under another key rejects it with retry configs, and a `HelloRetryRequest` that rejects it gets an outer hello naming the public name; and rustls's own ECH client keeps the inner hello it sealed.

This change builds against the faim-http commit `FAIM_HTTP_REF` names, which has the faim-template half.

## The server opens a client's ECH (faim-http#600)

FAIM substitutes its own keys into the ECH configs its clients read from DNS (faim-http's ADR-0026), so its client leg can open what they seal. Stock rustls has no server side of ECH. Everything here reads the hello's bytes as the client sent them, never a hello decoded and encoded again: the AAD is the outer hello with its payload zeroed, and the inner hello is rebuilt from the client's own extension bytes, so the transcript is the client's.

- **`server/ech.rs`** (new): `EchServerKey`, one `ECHConfig` as its publisher encoded it with the private key of its public key and those of the given HPKE suites the config names; HPKE's `info` is made of the given bytes. Opening tries each key whose config id and suite the hello names, and rebuilds the `ClientHello` an `EncodedClientHelloInner` stands for (RFC 9849 §5.1): the outer hello's session id, and each `ech_outer_extensions` replaced by the outer extensions it names, which must appear in the outer hello in its order and never name `encrypted_client_hello`. A hello under another key, a GREASE hello, a payload that fails to open, and one that opens to something that isn't an inner hello with zero padding are all not opened, never an error: a server reads each as GREASE.
- **`Accepted::open_ech`** and **`Accepted::ech_config_id`** (`server/server_conn.rs`): open a peeked hello's ECH before any handshake, so FAIM can decide how to answer, or relay the client's bytes untouched, and name the config id the hello's outer ECH carries, which says which configs to try. `open_ech` returns the inner hello's bytes, the `EncodedClientHelloInner` they were rebuilt from (faim-http#601), and which key opened it.
- **`ServerConfig::ech_keys`** (`server/server_conn.rs`, default empty in `server/builder.rs`): the keys the handshake opens a first hello with. **`server/hs.rs`**: `ExpectClientHello::with_certified_key` opens it and goes on with the inner hello from there, its SNI and signature schemes included; `ExpectClientHello::ech` keeps the HPKE context, and `handle` opens the second hello of a handshake that accepted the first's with it (RFC 9849 §7.1.1), failing the handshake where it doesn't (`PeerMisbehaved::EchNotOpenedAfterRetry`, `error.rs`): `missing_extension` for a hello with no outer ECH, `illegal_parameter` for one under another config id or suite or with an `enc`, `decrypt_error` for one that doesn't open. An opened inner hello that carries no inner `encrypted_client_hello`, or offers a version below TLS 1.3, fails with `illegal_parameter` (`PeerMisbehaved::IllegalEchInnerHello`, §7.1). A first hello's ECH that wasn't accepted stays rejected. One that decrypts to something that isn't an inner hello at all is read as GREASE, where §7.1 would abort: the client is broken either way, and a server that can't open its ECH answers it the same.
- **`server/tls13.rs`**: a `ServerHello` answering an accepted ECH ends its random with the acceptance confirmation, computed over the `ServerHello` with those eight bytes zeroed (RFC 9849 §7.2), a server template's as well as rustls's own; a `HelloRetryRequest` carries the confirmation in its `encrypted_client_hello` (§7.2.1). `tls13/key_schedule.rs` gains `server_ech_accept_confirmation`, since the client's version of it hangs off a key schedule the server doesn't have at that point.
- **`rustls/tests/faim_ech.rs`** (new, runner `tests/runners/faim_ech.rs`): a stock rustls client sealing to a key the server holds gets its ECH accepted, across a `HelloRetryRequest` too; a hello under another key is rejected with the retry configs; a peeked hello opens to its inner hello with the key that opened it; and a hello under another key, a GREASE hello and a tampered payload don't open.

A server template fitted to an inner hello sends none of the server's retry configs: faim-template counts `encrypted_client_hello` as offered only in its outer form (faim-http#600), so this change builds against the faim-http commit `FAIM_HTTP_REF` names.

## The server answers from a server template (faim-http#196)

FAIM answers its client in the shape of the answer the real server gave (its ADR-0011), so the client sees the server's JA4S, ALPN and ALPS. The template is plain data in faim-http's `crates/faim-template` (`ServerTemplate`), which fits it to the client's hello as an `Answer`: what of the server's answer goes out to this client, and what is left out as a `ServerShortfall`. The fork only picks what the answer names and sends what it renders.

- **`ServerConfig::hello_template`** (`server/server_conn.rs`, default `None` in `server/builder.rs`): the server's answer to answer the client with. `None` leaves the server stock. The template's ALPN takes the place of `alpn_protocols`.
- **`ServerConnection::template_shortfalls`** and `ServerConnectionData::template_shortfalls` (`server/server_conn.rs`): what of the template the connection couldn't send its client, for faim-http#197 to record on the connection.
- **`server/template.rs`** (new) holds the steps below, which the handshake calls.
- **`server/hs.rs`**, on a first hello:
  - The client's hello is read back with faim-template (`ClientHello::from_message`, from the hello's encoded bytes, so the extensions rustls doesn't parse count too) and the template fitted to it. A template that can't answer this client (another version, no key share for the server's group, a QUIC connection, a hello faim-template doesn't read) is a shortfall, and the server answers stock.
  - The template's version takes the place of rustls's pick: TLS 1.2 where the server answered in TLS 1.2, even to a client offering TLS 1.3 (faim-template refuses a template whose random says the server speaks TLS 1.3, which such a client would refuse).
  - The template's suite and group take the place of rustls's picks, where the crypto provider completes them. A suite it can't is a shortfall and rustls's pick stays. A group it can't drops the template, whose `ServerHello` names the group, and is checked before the template's version replaces rustls's: a TLS 1.2 template dropped after that would leave a client offering TLS 1.3 a stock TLS 1.2 answer carrying rustls's downgrade marker, which it refuses.
  - The server random ends with the template's downgrade marker where the server's did, and rustls's own marker is left off.
- **`server/tls13.rs`**:
  - `ServerHello`: the template's, rendered with the connection's random, the client's session id, the suite and the key share, and sent as rendered (`HandshakePayload::Unknown`), so its extensions keep the server's order.
  - `EncryptedExtensions`: the template's, rendered and sent as rendered. Its ALPN protocol becomes the connection's; a `record_size_limit` or `max_fragment_length` it agrees to caps what the server sends, below a smaller `ServerConfig::max_fragment_size`, which stays; early data is accepted as the resumption section below says.
  - A PSK is accepted only where the template's `ServerHello` resumed (faim-http#199).
  - `Certificate`: compressed with the template's algorithm where the server compressed its own and the config has a compressor for it, uncompressed otherwise; an OCSP response stapled only where the template's answer staples one, and a shortfall where it does and the certified key has none.
  - `ExpectFinished`, `ExpectCertificate` and `ExpectCertificateOrCompressedCertificate`: a client that agreed to the template's ALPS sends its own `EncryptedExtensions` first, before its certificate when asked for one and otherwise before its `Finished`, as Chromium does; it goes into the transcript.
- **`server/tls12.rs`**:
  - `ServerHello`: the template's, rendered with the connection's random, an empty session id and the suite, and sent as rendered. No ticket is issued, and a ticket or session id the client offers isn't resumed, since a resumed handshake would send rustls's own `ServerHello` (faim-http#199). ALPN and record size limits apply as on TLS 1.3.
  - Extended master secret only where the template's answer agreed to it.
  - `ServerKeyExchange`: signed with the template's scheme where the client offered it and the key signs with it, else rustls's pick and a shortfall.
  - `CertificateStatus`: sent where the template's answer staples, as on TLS 1.3; where the key has no response, `status_request` is left out of the `ServerHello` too.
